# Nova v0.9.9 — Resident Mode & Runtime Lifecycle

## Objetivo y estado

Nova 0.9.9 separa la visibilidad de la ventana de la vida real del proceso y endurece el updater residente para que una actualización incompleta no pueda convertirse en un arranque normal sobre una instalación incierta.

La versión sigue en desarrollo. No debe fusionarse ni publicarse hasta completar validación manual en Windows 11 y recibir aprobación explícita.

## Lifecycle residente

Estados principales: `starting`, `running`, `hidden`, `shutting_down`, `stopped`.

`request_window_close()` representa X. Si Resident Mode está habilitado y la bandeja confirmó readiness, usa `withdraw()` y pasa a `hidden`; hotkeys, wake word, F9, Perception, Gaming Awareness y política de Qwen continúan activos.

`request_shutdown(reason)` es idempotente. El lock físico de instancia no se libera dentro del lifecycle: `app.py` lo conserva hasta salir de `mainloop()` y lo libera en su `finally`.

`TrayController` declara `available=True` únicamente después de confirmar visibilidad real. Autostart usa HKCU y una entrada de otra instalación se considera conflicto, no se elimina.

## Instancia única e IPC

El scope de Windows es usuario + Session ID. El SID se utiliza en memoria y solo se persiste un hash derivado.

```text
%LOCALAPPDATA%\Nova\runtime\scope-<scope_id>\
  runtime.lock
  update_supervisor.lock
  owner.json
  commands\
```

`runtime.lock` protege la instancia residente y `update_supervisor.lock` un único supervisor de actualización. La autoridad es el lock del kernel, no PID/metadata.

`owner.json` identifica la generación con PID + creation time + `owner_id`. El IPC usa un archivo atómico por comando dirigido a `target_owner_id`; solo se aceptan `show`, `shutdown_for_update` y `status`.

## Supervisor y UI del updater

`update_runner.main()` adquiere `update_supervisor.lock` antes de coordinar el runtime. Cuando existe una transacción durable validada, el orden final es:

```text
supervisor mutex
→ runtime coordination / runtime guard
→ engine o recovery deja journal validado activo
→ verificar attempt_id + generation + estado
→ spawn del helper estable hash-validado
→ release runtime/recovery guard
→ CAS del intento exacto a cleared
→ helper observa cleared del mismo intento y lanza Nova una sola vez
→ release supervisor mutex
```

Un segundo supervisor devuelve **5** sin cerrar Nova, iniciar updater/pip, tocar `update_last.json` ni relanzar.

La UI no ejecuta shutdown local al pulsar **Actualizar**. Mantiene el `Popen` del supervisor, deshabilita el botón y hace polling con `root.after()` + `poll()`, nunca `wait()` en Tk.

## Motor interno sin autorización CLI

`--yes` deja de ser una capacidad interna. `update_runner.py`, ya dueño de supervisor mutex + runtime guard, importa `resident_update_engine` y ejecuta `run_supervised_update()` **en el mismo proceso**.

Las ejecuciones directas:

```text
python updater/resident_update_engine.py --yes
python updater/nova_updater_legacy.py --yes
```

fallan antes de consultar GitHub, crear stage, aplicar archivos o iniciar pip. `nova_updater.py`, UI y `.cmd` siguen delegando al supervisor.

El código legacy se conserva únicamente como implementación importable de compatibilidad; no constituye un entrypoint de actualización soportado.

## Journal schema 2 antes de cualquier mutación

La frontera transaccional queda fijada así:

```text
crear backup
→ validar backup
→ publicar update_recovery.json: transaction_prepared
→ preparar bootstrap estable de recovery
→ capturar snapshot de dependencias si requirements cambiará
→ files_applying
→ reemplazar/eliminar archivos + managed_files
→ files_applied
→ dependencies_starting si corresponde
→ dependencies_running
→ update_validation_in_progress
→ update_validated
→ handoff del supervisor
→ cleared
```

**No existe una mutación de la instalación anterior a `transaction_prepared`.** El journal se publica inmediatamente después de que el backup existe y fue validado.

`files_may_have_changed=true` se publica antes del primer reemplazo/eliminación. Si `requirements.txt` cambiará, `dependencies_may_have_changed=true` se publica en `dependencies_starting` **antes** de permitir que pip ejecute código.

Una muerte antes del backup/journal no deja una mutación del árbol administrado. Una muerte después de `transaction_prepared` siempre deja recovery requerido y el supervisor bloquea el relanzamiento según el journal, no solo según el exit code del motor.

Si la muerte ocurre exactamente después de `transaction_prepared` y antes de publicar la generación estable, `files_may_have_changed=false` permite reconstruir de forma segura `data/recovery_runtime/` desde el árbol todavía intacto. Esa reparación automática no se intenta después de que los archivos administrados pueden haber cambiado.

## Máquina de estados y compare-and-swap

`data/update_recovery.json` usa `schema_version=2` con:

- `attempt_id` obligatorio;
- `generation` monotónica;
- estado explícito;
- `recovery_required`;
- backup relativo validado;
- `files_may_have_changed`;
- `dependencies_may_have_changed`;
- `dependency_snapshot_path` + SHA-256 cuando aplica;
- identidades fuertes restantes;
- errores sanitizados.

Estados:

```text
transaction_prepared
files_applying
files_applied
dependencies_starting
dependencies_running
update_validation_in_progress
update_validated
pip_termination_unconfirmed
waiting_for_processes
rollback_in_progress
rollback_completed
rollback_validation_in_progress
rollback_validation_completed
dependency_repair_required
cleared
```

El grafo permitido está codificado. Cada transición obtiene un lock del journal, relee el archivo y exige que `attempt_id` y `generation` sigan coincidiendo con el payload del escritor. Solo entonces incrementa `generation` y publica por temporal + flush + `fsync` cuando corresponde + `os.replace`.

`cleared` es terminal: su conjunto de transiciones salientes es vacío. No existe `cleared → rollback_validation_completed`, ni siquiera `cleared → cleared`. Un launch fallido después del clear se diagnostica fuera del journal y no puede reabrir la transacción.

Esto impide que un escritor obsoleto sobrescriba otro intento, un rollback más avanzado o un estado de reparación. Los estados schema 1 conocidos se migran explícitamente; formatos truncados/desconocidos/no migrables fallan cerrados.

## Backup y rollback puro

El restaurador no escribe ni borra el journal. La máquina de estados marca `rollback_in_progress` **antes** de entrar al restaurador.

La restauración idempotente restaura `modified_existing`/`deleted_existing`, elimina solo `created_new`, restaura `managed_files.json`, revalida rutas del manifest, rechaza traversal/rutas externas/symlink escape, usa reemplazos atómicos cuando corresponde y no ejecuta pip.

Al terminar el motor/recovery coordinator alcanza:

```text
rollback_in_progress
→ rollback_completed
→ rollback_validation_in_progress
→ rollback_validation_completed | dependency_repair_required
```

`rollback_validation_completed` sigue con `recovery_required=true`; el clear terminal pertenece al handoff, no al restaurador ni al motor.

Un crash a mitad del rollback deja journal + backup y la siguiente ejecución puede repetir la restauración sin depender de cuál archivo quedó restaurado.

## Windows Job Object autoritativo

La garantía de terminación Windows no depende de snapshots `psutil.children()`.

Secuencia:

1. `CreateJobObjectW`;
2. `SetInformationJobObject` con `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
3. `CreateProcessW` de pip con `CREATE_SUSPENDED`;
4. `AssignProcessToJobObject`;
5. solo después, `ResumeThread`.

Si la contención no puede establecerse mientras pip sigue suspendido, pip no se considera iniciado. No existe fallback autoritativo a psutil.

El Job Object es la autoridad para confirmar que root/descendientes ya no pertenecen al contenedor. La CI Windows ejecuta una prueba real donde el updater muere con un proceso de dependencias dentro del Job y exige que el hijo no sobreviva; esa prueba falla CI si aparece como skipped.

## Identidades fuertes

Procesos pendientes se serializan como PID + creation time + rol técnico. PID reutilizado con otra creation time no representa al proceso original, no bloquea por esa identidad y nunca se mata solo por PID.

Errores de inspección/acceso se consideran incertidumbre y mantienen la cuarentena.

## Cuarentena persistente

**6 — `pip_termination_unconfirmed`** se usa cuando pip pudo ejecutar y no puede demostrarse la terminación autoritativa. No se inicia rollback concurrente ni se relanza Nova.

**7 — `recovery_required_or_in_progress`** bloquea startup/update cuando existe intento durable activo, recovery en curso, handoff no autorizado o journal no verificable.

Después de cualquier salida del motor, `update_runner` inspecciona `update_recovery.json`. Un rc inesperado con journal activo/corrupto devuelve 7 y **no relanza Nova**. El backup se conserva.

El updater gate no reescribe el journal del intento anterior mientras siga bloqueado por procesos fuertes; tampoco inicia nueva descarga/pip.

## Snapshot fuerte de dependencias

Antes de una actualización que modificará `requirements.txt`, Nova captura dentro del backup autorizado:

- conjunto completo de distribuciones normalizadas;
- versión exacta instalada de cada distribución;
- hash SHA-256 del snapshot;
- SHA-256 del `requirements.txt` anterior;
- lista acotada de imports críticos aplicables.

Después del rollback de archivos, si pip **nunca empezó**, basta la validación de archivos/sintaxis y no se inventa una reparación innecesaria.

Si pip **pudo ejecutar**, el entorno actual debe concordar con el snapshot previo. Se detectan distribución añadida/eliminada, versión cambiada, snapshot corrupto/hash incorrecto, requirements restaurado con entorno diferente y fallo de import crítico.

Los imports críticos se ejecutan en subprocess aislado/acotado con `python -I`; no se carga el asistente completo. Recovery nunca llama pip para instalar/desinstalar/degradar.

Una diferencia entra en `dependency_repair_required`, conserva journal + backup y bloquea el launch.

### Límite de `.venv`

El snapshot **valida** el estado; no implementa un rollback bit-a-bit de `.venv`. El `requirements.txt` actual tampoco es un lockfile reproducible completo. No se inventan versiones ni hashes.

## Bootstrap estable de recovery

Antes de aplicar archivos se publica una copia stdlib-only fuera del árbol gestionado normal:

```text
data/recovery_runtime/
  active.json
  generations/<uuid>/
    manifest.json
    recovery_bootstrap.py
    recovery_handoff.py
    recovery_state.py
    recovery_journal.py
    recovery_attempts.py
    recovery_files.py
    recovery_environment.py
    recovery_locking.py
```

Se escribe una generación nueva completa, se calculan/verifican hashes SHA-256 y solo entonces se reemplaza atómicamente `active.json`. La copia conocida como buena anterior no se sobreescribe simultáneamente.

`recovery_handoff.py` forma parte de la lista exacta del manifest. `app.py` y el propio handoff verifican el mismo conjunto y todos sus hashes; una copia estable alterada no puede ser utilizada como helper.

`app.py` permanece stdlib-only antes del gate. Orden:

```text
startup recovery gate
→ solo si permite continuar: _claim_instance
→ Tk/core/config/UI/Agent
```

Si el bootstrap administrado funciona, se usa. Si falla y existe journal, `app.py` valida manifest + hashes de la generación estable y ejecuta esa copia. Si ambas fallan, usa `MessageBoxW` directamente y sale con 7. `pythonw.exe` no depende de stderr como único canal.

## Handoff validado compartido

`recovery_handoff.py` es la implementación autoritativa para update y recovery. Solo acepta `update_validated` o `rollback_validation_completed`, ambos todavía con `recovery_required=true`.

Antes de crear el helper relee el journal y exige coincidencia exacta de `attempt_id`, `generation`, estado y cuarentena. Después valida `active.json`, el SHA-256 del manifest y el SHA-256 de los ocho módulos del bootstrap estable.

El helper recibe:

- `attempt_id` esperado;
- `generation` validada;
- estado de origen;
- token aleatorio de handoff;
- modo `post-update` o `post-recovery`;
- timeout acotado.

Orden de producción:

```text
supervisor mutex retenido
→ runtime/recovery guard retenido
→ verify exact validated journal
→ verify stable bootstrap hashes
→ Popen del helper estable
→ crash hook de prueba (si existe)
→ release runtime/recovery guard
→ CAS exacto a cleared, generation + 1, con token/mode/source state
→ helper observa ese cleared exacto
→ helper Popen(app.py, --post-update|--post-recovery) una vez
→ release supervisor mutex
```

El helper no lanza mientras el journal continúe activo. Si ve otro attempt, otra generation, otro estado, otro token, corrupción o timeout, termina con 7 sin ejecutar Nova.

### Fronteras de crash

- **Helper no puede iniciarse:** no se libera/limpia el intento y no hay Nova.
- **Muerte después del spawn, antes del guard release/CAS:** journal permanece validado + activo; helper expira sin launch.
- **Guard release falla:** no existe CAS a `cleared`; el helper sigue sin autorización.
- **CAS stale/otro writer:** la generación actual queda protegida y el helper no reconoce un `cleared` autorizado.
- **Muerte después del CAS:** el helper está desacoplado del supervisor y puede relanzar Nova exactamente una vez.
- **Popen final falla después de `cleared`:** se escribe `data/updater_logs/recovery_handoff.log`; no se modifica el journal terminal.

El wrapper `_launch_validated_handoff` de `update_runner.py` es el camino real de producción y delega a esta misma operación compartida. `recovery_bootstrap.py` usa la misma implementación para post-recovery.

## Recuperación reanudable y concurrencia

Cuando ya no quedan identidades fuertes bloqueantes, rollback/validation corre bajo:

```text
supervisor mutex
→ runtime/recovery guard
→ recargar journal
→ revalidar attempt/generation + backup
→ rollback/validation según estado durable
→ rollback_validation_completed
→ handoff validado compartido
```

Dos recovery supervisors reales no pueden restaurar/validar/relanzar simultáneamente. CI usa procesos `spawn` y locks del SO: solo uno entra; el segundo devuelve 7. Si se mata al propietario, el lock del kernel se libera y otro proceso reanuda desde el journal durable.

## Pruebas de crash real

`tests/_update_crash_worker.py` ejecuta el motor en subprocess y usa `os._exit(91)` en fronteras reales:

- journal creado antes de archivos;
- primer archivo reemplazado;
- mitad de apply;
- `files_applied`;
- dependencias marcadas como potencialmente mutables antes de pip;
- proceso dentro del Job Object en Windows;
- fallo de dependencias antes de rollback;
- mitad de rollback;
- archivos restaurados antes de validación;
- validación antes del handoff;
- update validado antes del handoff.

`tests/_handoff_crash_worker.py` agrega dos fronteras independientes:

- `os._exit(92)` después de iniciar el helper y antes de `cleared`: cuarentena persiste y no aparece launch;
- `os._exit(93)` después de `cleared`: el helper sobrevive y realiza el único `--post-update`.

## Privacidad

El journal/snapshot no persiste prompts, pantalla, teclado, tokens, variables de entorno ni comandos completos. Los errores se sanitizan; las identidades se limitan a datos técnicos requeridos para comparar identidad fuerte. El token de handoff es aleatorio y técnico, no contiene datos de usuario.

## Diagnóstico y recuperación manual

No borres `data/update_recovery.json`, `data/updater_backups/` ni `data/recovery_runtime/` mientras exista cuarentena.

```text
python updater/recovery_bootstrap.py --status
python updater/recovery_bootstrap.py --recover
```

Si el bootstrap administrado está roto, el MessageBox de `app.py` muestra el comando hacia la generación estable validada.

`dependency_repair_required` exige reparar/reconstruir explícitamente la `.venv`; no se debe limpiar el journal solo porque los paquetes requeridos “existen”.

## Códigos de salida

- `0`: operación completada.
- `3`: camino sin transacción durable completado pero falló el launch heredado.
- `4`: coordinación no verificable / entrypoint interno bloqueado.
- `5`: supervisor ya activo.
- `6`: terminación de pip no demostrada después de haber podido ejecutar.
- `7`: recovery requerido/en curso/no verificable, handoff no autorizado o intento durable activo tras salida anormal.

## Riesgos residuales

- No existe snapshot transaccional completo de `.venv`.
- Daño de disco/I/O o corrupción fuera de archivos administrados puede requerir intervención manual.
- El snapshot detecta diferencias de distribuciones/versiones, pero un requirements no fijado sigue sin ser un lock reproducible.
- Una vez publicado un `cleared` terminal, un fallo del proceso final de Nova no reabre automáticamente recovery; queda registrado y requiere un arranque/reintento normal posterior.
- Ante imposibilidad de demostrar identidad, journal, backup, hashes o validación, Nova mantiene la cuarentena.

## Validación manual pendiente en Windows 11

Usar exclusivamente una instalación/fixture descartable:

1. actualización normal;
2. doble clic sobre **Actualizar**;
3. timeout de pip con terminación confirmada;
4. terminación no confirmada simulada;
5. comprobar journal previo a mutación y cuarentena persistente;
6. crash entre `transaction_prepared` y bundle estable;
7. reiniciar Nova y Windows con cuarentena;
8. verificar bloqueo de startup y nuevo update;
9. esperar desaparición de identidades fuertes;
10. reanudar recovery y validar hashes/managed files;
11. verificar snapshot de dependencias y caso `dependency_repair_required`;
12. romper el bootstrap administrado y verificar fallback estable;
13. matar supervisor después del helper spawn y confirmar ausencia de launch;
14. matar supervisor después del CAS y confirmar exactamente un launch;
15. provocar fallo del Popen final y confirmar journal terminal sin reabrir.

La PR debe permanecer en draft hasta recibir esos resultados y aprobación explícita.

# Nova v0.9.9 — Resident Mode & Runtime Lifecycle

## Objetivo

Nova 0.9.9 separa la visibilidad de la ventana de la vida real del proceso y endurece el updater residente para que una actualización incompleta no pueda convertirse en un arranque normal sobre una instalación incierta.

La versión permanece en desarrollo. El cierre de esta fase exige CI verde en Ubuntu/Windows, validación manual sobre una instalación descartable y aprobación explícita antes del merge.

## Lifecycle residente

Estados principales: `starting`, `running`, `hidden`, `shutting_down`, `stopped`.

`request_window_close()` representa X. Si Resident Mode está habilitado y la bandeja confirmó readiness, usa `withdraw()` y pasa a `hidden`; no atraviesa el shutdown. Hotkeys, wake word, F9, Perception, Gaming Awareness y política de Qwen continúan activos.

`request_shutdown(reason)` es idempotente y realiza la limpieza del runtime. El lock físico de instancia no se libera dentro del lifecycle: `app.py` lo conserva hasta salir de `mainloop()` y lo libera en su `finally`.

## Bandeja y autostart

`TrayController` usa `pystray` fuera del hilo Tk y solo declara `available=True` después de confirmar visibilidad real. Un timeout, excepción o pérdida posterior de la bandeja produce modo degradado y evita dejar Nova invisible sin un mecanismo recuperable.

Autostart usa únicamente `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\NovaDesktop`, sin administrador. Una entrada que pertenezca a otra instalación se considera conflicto y no se elimina.

## Instancia única e IPC

El scope de Windows es usuario + Session ID. El SID se usa en memoria y solo se persiste un hash derivado.

```text
%LOCALAPPDATA%\Nova\runtime\scope-<scope_id>\
  runtime.lock
  update_supervisor.lock
  owner.json
  commands\
```

`runtime.lock` protege la instancia residente. `update_supervisor.lock` es un mutex independiente que protege la existencia de un solo supervisor de actualización. En ambos casos la autoridad es el lock del kernel, no un PID o archivo de metadata.

`owner.json` identifica cada generación con PID + creation time + `owner_id` aleatorio y rol. El IPC usa un archivo atómico por comando con `target_owner_id`; solo se aceptan `show`, `shutdown_for_update` y `status`. Comandos ajenos, viejos o malformados no se ejecutan.

## Supervisor único de actualización

`update_runner.main()` adquiere `update_supervisor.lock` antes de crear el log de esa ejecución, leer la versión, inspeccionar el runtime o enviar `shutdown_for_update`.

Orden normal obligatorio:

```text
supervisor mutex
→ runtime coordination / runtime guard
→ update o rollback
→ release runtime guard
→ launch
→ release supervisor mutex
```

No existe una rama que adquiera primero el runtime guard y después el supervisor mutex.

Si otro supervisor ya posee el mutex, la nueva ejecución devuelve **5 — actualización ya en curso**. Esa rama no envía shutdown, no ejecuta el updater, no modifica `update_last.json`, no inicia pip y no relanza Nova.

El mutex es un file lock del kernel; la muerte del propietario libera la exclusión aunque el archivo físico siga existiendo.

## UI del updater

`ui_workspace.py` no ejecuta `request_shutdown("update")` localmente. El supervisor es la única autoridad que envía `shutdown_for_update`, que el lifecycle convierte después en un shutdown normal de motivo `update`.

La UI conserva el objeto `Popen`, `_update_supervisor_active` y el botón de actualización. Después de un spawn correcto deshabilita el botón; doble clic o una nueva pulsación no crea otro supervisor local.

El seguimiento es Tk-safe y no bloqueante:

```text
root.after(...)
→ proc.poll()
→ reprogramar mientras siga activo
```

No se llama `wait()` en el hilo Tk. Si el supervisor termina mientras la UI original sigue viva, la misma sesión vuelve a consultar `update_last.json`, muestra el resultado una sola vez y rehabilita el botón. Si `Popen()` falla, Nova permanece abierta y el estado se restaura inmediatamente.

## Coordinación del runtime

El supervisor captura la identidad/proceso propietario antes de solicitar `shutdown_for_update`. En Windows la espera del runtime usa handles Win32 y creation time para no confundir PIDs reutilizados.

Una actualización solo puede modificar archivos después de confirmar la salida del runtime y adquirir el runtime guard exclusivo. El guard permanece retenido durante staging, reemplazo, dependencias, validación y rollback normal.

Si la coordinación falla antes de terminar el runtime, no se actualiza ni se lanza otra instancia. Si el runtime ya terminó pero no puede adquirirse/publicarse un guard verificable, tampoco se actualiza; la recuperación visible normal sigue usando código 4.

## Contención autoritativa de pip en Windows

La garantía anterior basada en `psutil.Process(pid).children(recursive=True)` no es suficiente para probar que no sobrevivió un hijo creado entre snapshots. En v0.9.9 esa garantía se sustituye por un **Windows Job Object**.

### Creación antes de ejecución

La ruta de Windows:

1. crea `CreateJobObjectW`;
2. configura `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` con `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
3. crea pip mediante `CreateProcessW` con `CREATE_SUSPENDED`;
4. asigna el process handle al Job mediante `AssignProcessToJobObject`;
5. solo después de una asignación válida ejecuta `ResumeThread`.

Pip no puede crear descendientes antes de estar contenido porque no se reanuda hasta completar la asignación.

Todas las estructuras/constantes/API usadas por `ctypes` declaran `argtypes` y `restype`. Los process/thread/job handles se cierran en los caminos de éxito y error.

En entornos donde Nova ya esté dentro de un Job se intenta la estrategia nativa compatible manteniendo al proceso suspendido. Una restricción de jobs anidados o un error de configuración/asignación que impida contención autoritativa provoca fallo **antes de ejecutar pip siempre que el sistema permita impedir su reanudación**. No existe downgrade silencioso a `psutil` como prueba de seguridad.

### Terminación y verificación

El Job Object es la autoridad de pertenencia del árbol en Windows. Al cerrar/terminar el Job se solicita la terminación de sus procesos y se consulta el estado del Job antes de declarar éxito. Que `TerminateProcess`, `TerminateJobObject` o `kill()` retornen no equivale por sí mismo a salida confirmada.

`psutil` puede seguir usándose para diagnóstico, pero no convierte una terminación en autoritativa.

El resultado de terminación representa, como mínimo:

- si pip llegó a arrancar;
- si existió contención autoritativa;
- si se solicitó cierre del contenedor;
- si terminó el proceso directo;
- si se confirmó la terminación del árbol;
- identidades fuertes todavía observadas;
- errores técnicos de inspección/cierre;
- si el rollback puede ejecutarse ahora;
- si debe activarse cuarentena.

Si el Job Object falla antes de reanudar pip, `dependency_started=false`: no se finge una terminación de un proceso que nunca ejecutó código y el rollback de archivos puede realizarse normalmente.

En Unix se mantiene una sesión/process group dedicado, señales y comprobación por identidades fuertes.

## Identidades fuertes de procesos

La recuperación no confía en un PID aislado. Cada proceso pendiente se serializa con identidad equivalente a:

```json
{
  "pid": 1234,
  "creation_time": 1720000000123456,
  "role": "pip_root_or_descendant"
}
```

Windows obtiene creation time desde la identidad nativa del proceso. POSIX normaliza una identidad estable derivada del arranque/proceso en lugar de depender de un float serializado de baja precisión.

Un proceso solo sigue siendo el registrado cuando **PID y creation time coinciden**. El mismo PID con otro creation time se considera reutilizado: no bloquea por la identidad anterior y nunca se mata únicamente por compartir PID.

Errores de acceso o inspección se registran de manera sanitizada y se tratan conservadoramente; una identidad cuya ausencia no puede demostrarse mantiene el estado fail-closed.

## Cuarentena persistente

Si pip arrancó y Nova no puede demostrar la terminación del contenedor/árbol, el updater devuelve **6 — `pip_termination_unconfirmed`**.

En código 6:

- no se inicia rollback concurrente;
- no se relanza Nova;
- `files_rollback_attempted=false`;
- no se afirma `files_rollback_ok=true`;
- se conserva backup + manifiesto;
- se crea un journal de recuperación obligatorio;
- `dependencies_may_have_changed=true` y `recovery_required=true`.

La salida del supervisor **no elimina** esa cuarentena. Persiste a través de nuevos arranques de Nova y reinicios de Windows.

Cualquier arranque o nueva actualización que encuentre recuperación pendiente, recuperación en curso, journal corrupto o esquema desconocido devuelve/propaga **7 — `recovery_required_or_in_progress`** en vez de cargar la aplicación normal o iniciar otra transacción.

## Journal atómico de recuperación

Archivo principal: `data/update_recovery.json`.

Esquema actual: `schema_version=1`. Incluye al menos:

```json
{
  "schema_version": 1,
  "attempt_id": "...",
  "generation": 1,
  "state": "waiting_for_processes",
  "recovery_required": true,
  "backup_path": "...",
  "created_at": "...",
  "updated_at": "...",
  "dependencies_may_have_changed": true,
  "files_rollback_attempted": false,
  "files_rollback_ok": false,
  "remaining_processes": [],
  "errors": []
}
```

Estados soportados:

```text
pip_termination_unconfirmed
waiting_for_processes
rollback_in_progress
rollback_completed
validation_in_progress
validation_completed
cleared
```

Cada transición se escribe en un temporal del mismo directorio, se hace `flush`, `fsync` cuando corresponde y se publica mediante `os.replace`. La corrupción JSON, truncado, versión de esquema desconocida o identidad inválida falla cerrado.

El journal no persiste variables de entorno, comandos completos, tokens, argumentos completos de procesos ni contenido de archivos.

### Validación del backup

`backup_path` es un identificador que debe resolver dentro de la raíz autorizada de backups de Nova. La recuperación aplica las mismas ideas de `safe_rel` del updater:

- no acepta `..`/traversal;
- no acepta rutas externas;
- rechaza componentes symlink que permitan escapar;
- valida cada ruta del manifiesto antes de restaurar;
- ninguna escritura puede salir de la instalación/raíces explícitamente permitidas.

Un backup inválido mantiene la cuarentena.

## Gate de startup antes de Nova normal

`nova/app.py` contiene un gate deliberadamente pequeño antes de la propiedad de instancia y del stack principal.

Orden real:

```text
imports stdlib de app.py
→ _startup_recovery_gate()
→ solo si permite continuar: _arguments()
→ _claim_instance()
→ importar tkinter
→ importar/install assistant.core_runtime
→ cargar config/UI/Agent
→ mainloop
```

Por tanto una cuarentena activa no construye Agent, no crea la UI completa y no inicia los servicios normales.

Si no hay journal pendiente, continúa el startup normal. Si existen identidades fuertes activas o errores de inspección, se muestra un aviso mínimo y se sale con 7. Si las identidades ya desaparecieron, el bootstrap intenta la recuperación bajo locks. Si el módulo mínimo de recovery no puede importarse pero el journal existe, `app.py` también falla cerrado.

El mensaje mínimo de Windows usa capacidades stdlib/Win32 y no necesita cargar el asistente completo.

## Gate antes de una nueva actualización

Con `update_supervisor.lock` ya adquirido, `update_runner` consulta primero el recovery gate. Una cuarentena existente tiene prioridad sobre cualquier nuevo update.

Mientras esté bloqueada:

- no se envía shutdown al runtime por una nueva transacción;
- no se descarga una nueva Release;
- no se reemplazan archivos;
- no se inicia pip;
- no se sobrescribe el journal del intento anterior;
- no se elimina el backup anterior;
- se devuelve código 7.

Si las identidades pendientes ya son seguras, el mismo gate puede completar la recuperación, pero **no encadena automáticamente una nueva actualización en esa ejecución**: primero deja la instalación recuperada y relanzada de forma controlada.

## Recuperación real, reanudable e idempotente

Cuando ninguna identidad fuerte registrada sigue viva o incierta, la recuperación usa este orden:

```text
supervisor mutex
→ runtime/recovery guard
→ recargar y validar journal
→ revalidar identidades
→ validar backup
→ rollback_in_progress
→ restauración idempotente
→ rollback_completed
→ validation_in_progress
→ validación de instalación
→ validation_completed
→ cleared
→ release runtime/recovery guard
→ launch único --post-recovery
→ release supervisor mutex
```

### Restauración

La restauración no ejecuta pip. Usa el backup/manifiesto para:

- restaurar archivos modificados;
- restaurar archivos eliminados;
- eliminar solo archivos `created_new` por la transacción fallida;
- restaurar `managed_files.json` a su estado previo;
- conservar los metadatos estrictamente necesarios del backup.

Las copias/reemplazos son repetibles. Si el recovery muere después de marcar `rollback_in_progress`, la siguiente ejecución vuelve a validar journal/backup y puede repetir la restauración sin depender de que cada archivo haya quedado en un punto exacto.

Si ya existe `rollback_completed`, el flujo puede continuar desde validación. Si existe `validation_completed` pero el launch final falló, la cuarentena se conserva en ese estado y el siguiente intento evita repetir el rollback y vuelve a intentar únicamente el launch seguro.

### Limpieza de cuarentena

La instalación debe pasar validación antes de que el estado se marque `cleared`/`recovery_required=false`. Un fallo de rollback, backup o validación conserva journal y backup y no inicia Nova.

El launch posterior se intenta una sola vez mediante `--post-recovery`, evitando recursión infinita entre bootstrap y aplicación normal.

## Alcance del rollback y riesgo residual

El rollback garantiza el árbol de **archivos administrados** que describe su backup/manifiesto; no es un snapshot completo del entorno Python.

Si pip llegó a ejecutarse, `.venv` puede contener cambios que restaurar archivos no revierte exactamente. La validación posterior comprueba que la instalación restaurada sea coherente para arrancar, pero no demuestra equivalencia bit a bit de todos los paquetes con el entorno previo.

El Job Object cierra la carrera conocida root→child en Windows porque el root no ejecuta antes de pertenecer al Job. Aun así, errores del sistema operativo, corrupción de disco, fallos de I/O o una instalación dañada fuera de los archivos administrados siguen siendo riesgos posibles; ante incertidumbre el diseño prioriza mantener la cuarentena.

## Códigos de salida relevantes

- `0`: operación correspondiente completada.
- `3`: update completado pero falló el relanzamiento normal.
- `4`: coordinación del runtime no verificada.
- `5`: supervisor de actualización ya activo.
- `6`: pip arrancó en la transacción actual y su terminación no pudo confirmarse; cuarentena creada.
- `7`: recuperación pendiente/en curso/corrupta o startup/update bloqueado por cuarentena.

## Nova Doctor y privacidad

Nova Doctor informa supervisor activo/inactivo mediante el mutex del kernel, último resultado de actualización y recovery pendiente. Si el journal está en `pip_termination_unconfirmed`/`waiting_for_processes`, puede mostrar únicamente las identidades/PID necesarios para el diagnóstico.

No se persisten argumentos completos de procesos, tokens, variables de entorno, prompts ni contenido de archivos. Los detalles técnicos se sanitizan.

## Pruebas automatizadas

Las suites específicas incluyen:

- `tests.test_updater_transaction`;
- `tests.test_update_runner`;
- `tests.test_updater_resident`;
- `tests.test_updater_diagnostics`;
- `tests.test_resident_process_ipc`;
- `tests.test_recovery_bootstrap`;
- `tests.test_recovery_update_gate`;
- `tests.test_pip_job_object`;
- suite completa con `unittest discover`.

Windows CI ejecuta pruebas reales del Job Object. Verifica `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, orden assign-before-resume, fallo de setup antes de ejecutar pip, restricciones de jobs anidados, limpieza de handles, cierre de root+child y el caso donde el root crea un hijo y sale rápidamente. La carrera root→child se repite varias veces.

Recovery tests cubren PID+creation-time, PID reutilizado, inspección conservadora, gate antes de `_claim_instance`, cuarentena sin Agent/UI, bloqueo de nuevos updates, hashes restaurados, archivos eliminados/creados, `managed_files`, validación, crash a mitad del rollback, reanudación idempotente, dos recoveries concurrentes, journal corrupto/truncado y traversal/symlink.

## Procedimiento manual de diagnóstico/recovery

No borrar `data/update_recovery.json` ni el backup para “forzar” el arranque. Eso elimina la barrera sin resolver la incertidumbre.

Para diagnosticar:

1. conservar `data/update_recovery.json`;
2. conservar `data/updater_backups/` y logs;
3. comprobar estado/identidades con el recovery bootstrap o Nova Doctor cuando sea seguro;
4. si sigue esperando procesos, no matar un PID solo por coincidir: la identidad debe incluir creation time;
5. si recovery automático falla, trabajar sobre una copia/fixture y revisar el error sanitizado/backup antes de cualquier intervención manual.

La restauración manual fuera del recovery validado queda como última medida y no debe ejecutarse sobre la instalación principal para probar escenarios de fallo.

## Checklist manual pendiente — Windows 11

Usar una instalación/fixture descartable:

1. actualización normal;
2. doble clic rápido en Actualizar;
3. timeout de pip con terminación Job Object confirmada;
4. escenario seguro/simulado de terminación no confirmada;
5. creación de cuarentena persistente;
6. reinicio de Nova con cuarentena activa;
7. reinicio de Windows con cuarentena activa;
8. confirmar bloqueo del arranque normal;
9. confirmar bloqueo de un nuevo update;
10. esperar/simular desaparición de las identidades fuertes originales;
11. comprobar recovery reanudado;
12. comprobar restauración exacta de archivos + `managed_files` y validación;
13. comprobar un único relanzamiento `--post-recovery`;
14. simular fallo de recovery y confirmar que journal + backup permanecen.

No provocar estos fallos destruyendo la instalación real de uso diario.

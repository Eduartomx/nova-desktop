# Nova v0.9.9 — Resident Mode & Runtime Lifecycle

## Objetivo

Nova 0.9.9 separa la visibilidad de la ventana de la vida real del proceso. Ocultar Nova no cierra Agent, hotkeys, wake word, Perception, Gaming Awareness ni Qwen. La salida real se coordina mediante `RuntimeLifecycleManager` y la propiedad del runtime permanece protegida hasta el final del proceso.

## Lifecycle

Estados: `starting`, `running`, `hidden`, `shutting_down`, `stopped`.

`request_window_close()` representa X. Si Resident Mode está habilitado y la bandeja confirmó readiness, usa `withdraw()` y pasa a `hidden`. No atraviesa el shutdown.

`request_shutdown(reason)` es idempotente y ejecuta en Tk: bloquea trabajo nuevo, detiene voz/wake, Gaming/Perception, Browser Agent, guarda estado, aplica `unload_on_exit`, detiene bandeja/hook de sesión, difiere la liberación de instancia y destruye Tk. Un fallo de un componente se registra y no impide continuar.

El lock físico no se libera dentro del lifecycle: `app.py` lo mantiene hasta salir de `mainloop()` y lo libera en su `finally`.

## Bandeja

`TrayController` usa `pystray` fuera del hilo Tk. Con un `setup` personalizado establece explícitamente `icon.visible = True`; `available=True` solo se establece después de volver a confirmar que el backend/icono quedó visible. Excepción, icono no visible o timeout producen `degraded=True`.

Cada intento de `start()` usa una generación y `Event` propios. Un callback tardío de una generación expirada no puede validar otra posterior y un timeout detiene solo el icono de ese intento.

Si una bandeja ya operativa se degrada mientras la ventana está oculta, la restauración se solicita mediante el lifecycle, que vuelve al scheduler Tk. El hilo de pystray no manipula widgets directamente. Con bandeja degradada X cierra normalmente y `--background` permanece visible, evitando procesos invisibles sin icono recuperable.

## Instancia única por usuario y sesión

En Windows la identidad usa el SID del usuario obtenido en memoria y Windows Session ID. El SID no se persiste: se guarda solo un hash. El scope se deriva de hash de usuario + Session ID.

Ruta: `%LOCALAPPDATA%\Nova\runtime\scope-<scope_id>\` con `runtime.lock`, `update_supervisor.lock`, `owner.json` y `commands\`.

`runtime.lock` protege la única instancia residente. `update_supervisor.lock` es un mutex separado que protege la existencia de un único supervisor de actualización en el mismo usuario/sesión. Ambos usan el lock del kernel como autoridad; no se usa PID, booleano ni metadata como sustituto de exclusión.

`owner.json` se escribe atómicamente para el runtime/guard y registra PID, tiempo real de creación del proceso, `owner_id` aleatorio/generación, rol (`runtime` o `updater`), scope, hash de usuario, Session ID y timestamp. El mutex del supervisor usa `publish_owner=False`, por lo que no compite ni sobrescribe esa metadata.

Los probes/guards del updater adquieren primero el lock del runtime sin sobrescribir la metadata previa. La identidad anterior se valida bajo exclusión y solo entonces se publica el rol `updater`. Esto permite detectar reutilización de PID mediante PID + creation-time y recuperar metadata obsoleta sin confundir otro proceso con Nova.

## IPC dirigido por generación

No hay sockets, puertos ni servidor de red. Cada orden es un archivo atómico independiente con `command_id`, `target_owner_id`, `command` y `created_at`.

Comandos permitidos: `show`, `shutdown_for_update`, `status`.

Una instancia consume solo mensajes para su propio `owner_id`. Mensajes malformados, vencidos o de otra generación se eliminan sin ejecutarse. Un archivo por comando evita sobrescrituras entre emisores concurrentes.

Antes de escribir, el buzón valida que el `target_owner_id` coincida con el propietario publicado y que su rol sea `runtime`. Durante el guard del updater no se pueden dirigir comandos al proceso de actualización.

Una segunda ejecución normal no carga Agent/Tk/servicios. Si no puede identificar al propietario o entregar `show`, termina con código distinto de cero.

## Autostart

Se usa únicamente `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\NovaDesktop`, sin administrador ni servicio. El comando usa la instalación real, `--background` y quoting seguro.

Al desactivar, Nova elimina la entrada solo si coincide exactamente con la instalación actual. Si pertenece a otra instalación devuelve `entry_belongs_to_other_installation` y no modifica el registro. Está desactivado por defecto.

## Updater seguro

### Mutex único del supervisor

`update_runner.main()` intenta adquirir `update_supervisor.lock` **antes** de crear log, leer versión, inspeccionar `owner.json`, construir el mailbox o coordinar el runtime. El orden obligatorio es:

```text
supervisor mutex
→ runtime coordination / runtime guard
→ update o rollback
→ release runtime guard
→ launch/recovery launch
→ release supervisor mutex
```

No existe una rama que adquiera primero el guard del runtime y luego el mutex del supervisor.

Si el mutex ya pertenece a otro proceso, el segundo `update_runner` termina inmediatamente con código **5 (`actualización ya en curso`)**. Esa rama no envía `shutdown_for_update`, no llama `run_update()`, no escribe `update_last.json`, no intenta `launch_nova()` y no altera el resultado del supervisor propietario. Esto aplica de la misma forma a UI, `ACTUALIZAR_NOVA.cmd` y ejecución directa.

Como el mutex es un file lock del kernel, la muerte del proceso propietario libera la exclusión por el mecanismo del sistema operativo; un archivo huérfano no mantiene una actualización bloqueada permanentemente.

### La UI no inicia cierres ni supervisores duplicados

Al pulsar **Actualizar**, `ui_workspace.py` no ejecuta `request_shutdown("update")`. La UI valida `update_runner.py`, lanza el supervisor con `--parent-pid`, guarda el objeto `Popen`, activa `_update_supervisor_active` y deshabilita el botón.

Un doble clic rápido o una segunda pulsación mientras ese proceso siga vivo no crea otro `Popen`; muestra `Actualización ya en curso`. Este bloqueo local es solo UX: la protección real entre UI/CMD/directo sigue siendo `update_supervisor.lock`.

La UI no llama `wait()` desde Tk. Consulta `proc.poll()` mediante `root.after()`. Mientras el supervisor continúa vivo puede mostrar `Actualización en curso…`. Si Tk ya fue destruido porque el supervisor pidió correctamente el shutdown, un callback tardío se ignora de forma segura.

Si el supervisor termina mientras la instancia original continúa abierta, la UI vuelve a consultar `update_last.json`, evita consumir el mismo token dos veces, muestra el resultado en esa misma sesión, limpia `_update_supervisor_active` y rehabilita el botón. Código `4` se presenta como fallo de coordinación con Nova aún abierta; código `5` se presenta como otra actualización ya activa y no como rollback/corrupción. Si `Popen()` falla, el estado se revierte inmediatamente y Nova permanece abierta.

### El supervisor es la única autoridad de cierre

El único componente que envía `shutdown_for_update` es `update_runner.py`. `RuntimeLifecycleManager.handle_control_command("shutdown_for_update")` conserva la traducción a `request_shutdown("update")`, por lo que el cierre sigue recorriendo el lifecycle real y no existe un segundo camino local desde la UI.

### Coordinación exception-safe

`update_runner.py` captura el proceso antes de enviar `shutdown_for_update`. En Windows usa HANDLE con `SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION` y firmas explícitas para `OpenProcess`, `GetProcessTimes`, `WaitForSingleObject` y `CloseHandle`.

Errores operacionales normales durante importación de componentes, construcción/lectura del lock, metadata, mailbox, captura del proceso, adquisición o publicación del guard se convierten en un `ShutdownCoordination` de fallo. `KeyboardInterrupt` y `SystemExit` no quedan atrapados por esta frontera.

Si el fallo ocurre **antes** de una terminación verificada, el updater no se ejecuta, no se lanza una segunda instancia, el estado se escribe best-effort y se intenta `show` contra el runtime existente cuando su identidad es válida.

Si el proceso anterior ya terminó de forma verificable pero la coordinación falla antes de obtener un guard válido, tampoco se ejecuta el updater. Cualquier guard retenido se libera best-effort y el supervisor intenta exactamente un relanzamiento visible de recuperación con `--post-update`; el código de salida permanece en `4`.

Después de esperar la terminación real y adquirir el guard con rol `updater`, este permanece retenido durante descarga, staging, reemplazo, dependencias, validación y cualquier rollback.

### Terminación verificable del árbol de pip

`pip install -r requirements.txt` usa timeout predeterminado de **900 segundos (15 minutos)**, inyectable para pruebas. Valores no positivos/no finitos se rechazan y valores superiores a una hora se limitan a `3600`. No se usa `shell=True` ni un timeout externo que mate todo `nova_updater.py`.

Pip se inicia de forma contenible: `start_new_session=True` en Unix y `CREATE_NEW_PROCESS_GROUP` en Windows. `pip_safety.py` obtiene un snapshot del proceso y descendientes; en Windows usa `psutil.Process(...).children(recursive=True)`, y en Unix combina descendientes con el grupo de procesos de la nueva sesión.

Ante timeout la secuencia es:

1. snapshot inicial del árbol;
2. terminación limpia del proceso/grupo;
3. espera acotada del proceso directo;
4. nuevo snapshot + comprobación de procesos vivos;
5. si queda algo, nuevo snapshot justo antes de la fuerza para reducir la carrera de descendientes nuevos;
6. kill del árbol restante;
7. espera/reap final del proceso directo;
8. snapshot final y comprobación de PIDs vivos.

El resultado estructurado incluye `terminated_confirmed`, `direct_process_terminated`, `remaining_pids`, `termination_errors` y `detail`. Una excepción de inspección también impide declarar la terminación como confirmada. Nunca se interpreta `kill()` por sí solo como prueba de salida.

#### Terminación confirmada

Solo si el proceso directo fue reapeado/verificado, la inspección fue completa y no quedan descendientes conocidos vivos se usa el mensaje **“pip y sus descendientes fueron detenidos y esperados de forma verificable”**. Entonces la transacción considera que pip sí llegó a iniciarse, ejecuta rollback de archivos, conserva backup y persiste:

- `files_rollback_ok` según el resultado real;
- `files_rollback_attempted=true`;
- `dependencies_may_have_changed=true`;
- `recovery_required=true`.

Después el supervisor libera el guard del runtime y realiza su único relanzamiento visible normal.

#### Terminación no confirmada: fail-closed

Si después de terminate + kill + waits + inspección final la terminación no puede confirmarse, se lanza `PipTerminationUnconfirmedError` y `nova_updater.py` devuelve código **6**.

En esa rama **no comienza el rollback** porque pip o un descendiente todavía podría modificar la instalación. El backup y `backup.json` permanecen intactos. `data/update_recovery.json` registra:

- `status="pip_termination_unconfirmed"`;
- `files_rollback_ok=null`;
- `files_rollback_attempted=false`;
- `dependencies_may_have_changed=true`;
- `recovery_required=true`;
- solo los `remaining_pids` y errores técnicos de terminación necesarios.

No se declara que los archivos fueron restaurados y no se incluyen argumentos completos de procesos, tokens, contenido de archivos ni rutas externas sensibles.

El supervisor conserva el guard mientras `nova_updater.py` realiza toda la escalada y verificación. Solo después de recibir el código `6` libera el guard; **no relanza Nova desde esa `.venv`**. Esta excepción rompe deliberadamente la regla normal de relanzamiento para impedir ejecutar Nova sobre un entorno que podría seguir mutando.

### Alcance del rollback

El rollback transaccional cubre los **archivos administrados por Nova**. El manifiesto distingue `modified_existing`, `deleted_existing`, `created_new` y `unchanged`; restaura los dos primeros desde backup, elimina solo `created_new`, no toca `unchanged` y restaura el estado previo de `managed_files.json`. Los reemplazos viables usan temporal + `os.replace()`.

Incluso tras un rollback de archivos completamente correcto, si pip alcanzó a iniciarse no existe una reversión demostrable del estado exacto de `.venv`. `dependencies_may_have_changed=true` y `recovery_required=true` lo expresan explícitamente. Una reconstrucción/versionado completo de `.venv` queda fuera del alcance de v0.9.9.

## Windows shutdown/logoff

`windows_session.py` integra `WM_QUERYENDSESSION` y `WM_ENDSESSION`: responde rápido a la consulta y solicita shutdown real cuando Windows confirma fin de sesión/apagado.

## Diagnóstico

Nova Doctor agrega `Updater residente`. El estado activo/inactivo del supervisor se obtiene intentando el mutex del kernel, no leyendo un PID. También informa último resultado disponible, recuperación pendiente y si existe `pip_termination_unconfirmed`; los PID restantes solo se muestran en esa última condición.

## Pruebas

Ubuntu ejecuta `compileall` y la suite completa. Windows ejecuta explícitamente lifecycle, owner/IPC, updater, rollback, session shutdown, Gaming Awareness, Instant Wake/hotkeys y procesos separados reales.

`test_resident_process_ipc.py` reproduce además dos supervisores simultáneos reales en Windows: solo el propietario entra a coordinación, `run_update()` y launch; el segundo devuelve `5`. La prueba se repite dentro del bloque sensible a carreras y también comprueba que matar al propietario libera el mutex del kernel.

`test_updater_resident.py` cubre doble clic, supervisor activo, fallo de `Popen`, códigos `4` y `5`, resultado disponible en la misma sesión, rehabilitación del botón, ausencia de shutdown local y ausencia de `wait()` en el hilo Tk.

`test_update_runner.py` valida código `5` sin tocar estado/IPC/updater/launch, orden de locks, liberación del mutex ante éxito/error/excepción/fallo de launch y la excepción de código `6` sin relanzamiento.

`test_updater_transaction.py` usa archivos reales y SHA-256 y además simula sin sleeps reales: pip normal, terminate exitoso, escalada a kill, excepción de terminate, kill sin salida real, último wait expirado, descendientes restantes, rollback permitido solo con terminación confirmada y fail-closed sin rollback cuando no se puede confirmar.

`test_updater_diagnostics.py` valida scope del mutex y minimización de datos del diagnóstico.

## Privacidad

Resident Mode no añade screenshots periódicos, captura de teclado, memoria de juegos, telemetría externa ni servidores de red. Los archivos de control contienen solo metadata técnica de ejecución/alcance.

## Validación manual pendiente en Windows 11

1. Abrir Nova normalmente.
2. X → bandeja sin detener servicios.
3. Restaurar por hotkey y bandeja.
4. Probar wake word y F9 oculta.
5. Probar Gaming Mode y restauración de Qwen oculta.
6. Lanzar Nova por segunda vez y comprobar que restaura la primera.
7. Activar/desactivar autostart y validar login real.
8. Probar una entrada HKCU de otra instalación y confirmar conflicto sin borrado.
9. Probar doble clic en **Actualizar** y arranques simultáneos desde UI/CMD/directo; debe existir un solo supervisor.
10. Confirmar que Nova permanece abierta hasta que el supervisor envía `shutdown_for_update`.
11. Simular un fallo de `Popen()` y comprobar que botón/estado se restauran sin cerrar Nova.
12. Ejecutar una actualización real desde una Release anterior y verificar un solo `--post-update` visible.
13. En entorno controlado, provocar timeout de pip con terminación confirmada y revisar rollback + `data/update_recovery.json`.
14. En entorno aislado, validar la presentación de `pip_termination_unconfirmed` sin relanzar Nova automáticamente.
15. Salir desde bandeja y confirmar que no queda proceso Nova.
16. Reiniciar y verificar que no existen listeners/servicios duplicados.

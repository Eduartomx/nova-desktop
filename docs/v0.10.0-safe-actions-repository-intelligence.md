# Nova v0.10.0 — Safe Actions & Repository Intelligence

## Estado

Implementación en rama de desarrollo. El cambio debe pasar revisión de diff, CI completa en Ubuntu/Windows y validación manual controlada en Windows 11 antes de autorizar merge o publicación. v0.9.9 continúa siendo la release estable mientras la PR permanezca en draft.

Minecraft Agent y Hexabot no forman parte de esta versión.

## Action Broker

`ActionBroker` es la única autoridad del dispatcher de herramientas antes de producir efectos. Una solicitud incluye un `request_id` aleatorio, herramienta, clase de efecto, riesgo, objetivo sanitizado, motivo, hash SHA-256 de herramienta + argumentos normalizados, tarea, owner, scope, sesión, tiempos y estado.

Los estados son `pending`, `approved`, `denied`, `expired`, `cancelled` y `executed`. Una aprobación solo puede consumirse una vez. El audit log conserva únicamente metadatos acotados y hashes; nunca argumentos completos, comandos, texto escrito, portapapeles, secretos ni contenido de formularios.

### Perfiles

- `safe`: confirma efectos reversibles, mutaciones y alto riesgo; las lecturas sensibles exigen intención explícita y confirmación.
- `balanced`: valor para instalaciones nuevas; permite lecturas y efectos locales reversibles, confirma mutaciones y alto riesgo.
- `trusted`: conserva automatización local de bajo/medio riesgo, pero las lecturas sensibles siguen exigiendo intención explícita y el alto riesgo sigue pidiendo permiso de una vez.

La migración conserva un perfil antiguo explícito. Si una configuración previa no tenía perfil, cualquier `confirm_*` activado migra a `safe`; una configuración histórica con todas las confirmaciones desactivadas permanece `trusted`.

### Clases y rechazos permanentes

Las herramientas se clasifican como `read_only`, `sensitive_read`, `reversible`, `mutating`, `high_risk` o `forbidden`. Una herramienta desconocida falla cerrada.

PowerShell genérico no se considera aislado por una expresión regular. En v0.10.0 sólo una lista positiva estrecha de consultas simples y deterministas puede llegar a autorización. El ejecutable se obtiene del directorio de Windows consultado al sistema y se valida bajo `System32` o `Sysnative`; ni `PATH` ni el directorio actual participan. Aliases, composición dinámica, call operator, cadenas, pipelines, comandos concatenados, shells anidados, contenido codificado y sintaxis no comprendida se rechazan antes de mostrar UI o invocar subprocess. Borrado masivo, formato/inicialización, arranque, apagado/reinicio, seguridad, protecciones y credenciales continúan siendo imposibles de autorizar.

`open_app` sólo admite aliases registrados y vuelve a resolver el binario en una ubicación confiable inmediatamente antes de ejecutar con `shell=False`. Los documentos usan la herramienta separada `open_document`, limitada a roots y extensiones explícitas. Rutas arbitrarias, ejecutables, scripts, UNC, esquemas y tipos desconocidos se rechazan antes de UI o apertura.

### Aprobar, denegar y detener

La tarjeta Tk muestra herramienta, riesgo, efecto y objetivo sanitizado. Sus únicas decisiones son:

- permitir una vez;
- permitir durante la tarea, solo cuando la política lo admite;
- denegar.

Alto riesgo no admite grant de tarea. Cerrar la tarjeta equivale a denegar y el timeout produce `expired`. El permiso no puede llegar desde el LLM, web, archivo, pantalla, clipboard, voz, IPC o texto remoto.

El botón **Detener** y la opción **Detener automatización** de la bandeja cancelan solicitudes pendientes. Puede configurarse `security.emergency_stop_hotkey`, vacío por defecto para no registrar un nuevo hotkey global sin decisión del usuario.

### Revalidación y Task Engine

Antes de ejecutar, Nova vuelve a comprobar argumentos, owner, scope, sesión, tarea y contexto observado. Para archivos incluye existencia, tamaño, tiempo y hash acotado; para Browser/UI incluye URL, formulario, ventana y control. Cualquier cambio invalida el permiso.

`browser_fill` con submit solicita permiso antes de rellenar. Enter, UIA y mouse se tratan como alto riesgo para impedir rutas alternativas. `write_file` se autoriza antes de crear directorios, generar backup o escribir.

Task Engine registra `waiting_for_approval` sin considerarlo fallo, retry, replan ni timeout de autonomía. Cancelar la tarea, shutdown o update libera la espera. El checkpoint solo conserva metadatos sanitizados.

La espera ocurre en el mismo worker y conserva `task_id`, índice de paso y callback. Aprobar desbloquea esa misma ejecución; no se llama nuevamente al Planner ni se reconstruyen argumentos. Si no existe UI local, la operación termina como `approval_ui_unavailable`. Una reapertura de proceso expira cualquier aprobación irrecuperable y exige crear una solicitud nueva.

Los grants incluyen tarea, owner, scope, sesión y herramienta. El broker barre expiración al crear, consultar, aprobar, denegar, cancelar, consumir y podar; esto cubre solicitudes `pending` y `approved` que un worker abandonó sin consumir. La comprobación de capacidad y la inserción son atómicas bajo el mismo lock. La poda conserva estados activos, y el audit JSONL usa escritura atómica y rotación por tamaño con un número pequeño de archivos.

### Intención humana y DOM

Las lecturas sensibles sólo aceptan intención derivada de una orden humana local positiva y exacta; negaciones, menciones genéricas, citas y ejemplos no bastan. Se representa mediante hash, procedencia, `request_id` y sesión, y se propaga con contexto de ejecución inmutable. No existe un campo compartido en `LocalTools` o Task Engine que otra conversación pueda sobrescribir o heredar. Planner, Executor, memoria, skills, web, archivos, commits y releases no pueden crearla.

Todo acceso Playwright usado para autorizar ocurre dentro del worker serializado. En una sola captura se ligan URL completa mediante hash, origen, selector resuelto, identidad del elemento, tipo, `href`, `onclick`, formulario, método, action y `formaction`; el snapshot se repite inmediatamente antes del consumo. Sólo un enlace pasivo HTTP(S), sin JavaScript, download, formulario ni rol de botón, conserva política inferior. Botones, inputs, roles de botón, formularios, destinos no seguros y cualquier inspección ausente, fallida o ambigua escalan a `high_risk`. Los permisos de tarea nunca cubren un submit.

## Repository Intelligence

`GitHubReadClient` usa solo biblioteca estándar (`urllib`) y el repositorio fijo de `updater/update_config.json`. Acepta únicamente HTTPS hacia `api.github.com`, envía User-Agent, usa timeout y ETag, limita tamaño y gestiona 404, rate limit, timeout, JSON corrupto y respuestas sobredimensionadas.

No usa `gh`, token, cookies, sesión de navegador ni autenticación. El modelo, una página o un archivo no pueden elegir otro repositorio o URL. La cache pública es acotada y se reemplaza atómicamente; es solo informativa y nunca participa en la autorización de updates ni sustituye validación criptográfica.

### Fuentes y funcionamiento offline

- `VERSION`, `nova/NOVA_VERSION.txt` y `assistant.__version__` para versión local;
- `data/update_last.json` para el último rango aplicado;
- `CHANGELOG.md` local para novedades;
- última release pública, commits y archivos acotados del repositorio propio;
- cache ETag cuando GitHub no está disponible.

Cada respuesta indica fuente y timestamp: `CHANGELOG.md local`, `release vX.Y.Z`, `cache consultada` o `GitHub no disponible`. El modo offline nunca inventa la versión remota.

### Herramientas y routing

- `nova_version_status`
- `nova_whats_new`
- `nova_repository_activity`
- `nova_repository_file`

El routing determinista anterior al LLM cubre consultas de versión, novedades, actualización, changelog y estado del repositorio. `nova_repository_file` restringe traversal, tamaño, repositorio y ref (`main`, latest o tag/SHA validado), y devuelve el contenido marcado como externo no confiable.

## Privacidad y límites

Repository Intelligence es de solo lectura, no crea issues/PR, no descarga ejecutables y no ejecuta contenido. Repositorios, releases, commits, issues y PR nunca son instrucciones de sistema ni autorización. El Action Broker no almacena valores sensibles y no permite aprobaciones remotas.

## Validación

El gate focal ejecuta en Ubuntu y Windows las suites de broker, política, aislamiento concurrente de intención, aplicaciones/PowerShell, Task Engine, UI, guardas de herramientas, cliente/cache, routing y harness antes de la suite completa. Los tests de red usan mocks y los de UI/entrada no mueven mouse, escriben ni cierran ventanas reales.

Para la validación manual controlada en Windows 11 se usa:

```powershell
py -3.11 tools\validate_v010_windows.py --expected-head <HEAD_REVISADO>
```

El harness exige Windows 11 por build (`>= 22000`), registra edición/versión/build, comprueba el HEAD, ejecuta y cronometra las suites focales y lanza una copia descartable de Nova con `LOCALAPPDATA` aislado. Cada checkpoint incluye precondición, pasos y resultado observable; sólo `PASS` confirmado es éxito. Las acciones de archivo permanecen dentro de la fixture.

Los procesos se atribuyen a la fixture por ruta/cmdline y ascendencia, se clasifican por rol y se complementan con threads de Nova e identidad publicada en `owner.json`; un Python ajeno no cuenta como runtime. Antes/después se comprueban solicitudes, workers y procesos huérfanos. `FAIL` o `NOT_RUN` obligatorio producen salida distinta de cero. La evidencia JSON/ZIP se sanitiza antes de escribir y no contiene contenido de archivos, comandos, prompts, portapapeles, títulos privados, PID en claro, tokens ni secretos. La validación no realiza compras, envíos, publicaciones, borrados ni comandos destructivos.
